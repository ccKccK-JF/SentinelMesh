# SentinelMesh 面试讲解手册

这份手册用于把“做了什么、为什么这样做、底层如何工作、边界在哪里”讲清楚。回答时只陈述仓库中已经实现和验证的内容；生产化方向可以作为演进方案，但不要说成已经上线。

## 1. 一分钟项目介绍

> 我做了一个 Linux 服务器性能诊断和自适应路由平台。节点侧用 C++ 采集 procfs 的 CPU、内存、Load 和网络指标，并通过 eBPF 跟踪调度等待、块 I/O 延迟、TCP RTT、重传和 RST；控制面用 Go 接收 gRPC 双向流，根据序列号做幂等处理，再用 EWMA、硬门槛、滞回和恢复冷却计算节点健康状态。异常节点会被路由策略降为零权重，恢复后从 10% 开始在 60 秒内渐进增权。项目还接入了 Prometheus/Grafana，并通过 stress-ng、fio、iperf3、tc netem 和确定性对照实验做验证。整个仓库约 5,026 行手写核心代码、测试与脚本。

如果面试官继续问，优先展开三个难点：eBPF 观测如何低开销聚合、遥测链路如何处理断线与重复、状态机如何避免流量抖动。

## 2. 三分钟项目介绍

### 背景

传统资源监控能看到 CPU 很高，却不一定能解释服务为什么变慢。例如 CPU 利用率不高但任务长期排队，可能是调度竞争；磁盘吞吐量不大但 P99 很高，可能是尾延迟；网络带宽正常但重传和 RTT 上升，也会直接影响请求。

### 架构

节点 Agent 用 C++ 实现，因为它要直接调用 libbpf、读取 BPF Map、控制内存布局和资源生命周期。普通低频指标走 procfs，只有内核路径上的延迟和异常事件才使用 eBPF。Agent 在本地按窗口聚合，再通过 Protobuf 批次发给 Go 控制面。

控制面负责三件事：第一，维护 Agent 双向流与节点生命周期；第二，保存最新快照并计算健康状态；第三，生成带版本号的路由权重。查询、Prometheus 导出和假网关都消费同一份快照，避免多个模块各算一套结果。

### 难点

1. eBPF 热路径不能做复杂工作，所以使用 per-CPU 对数直方图和计数器，用户态再跨 CPU 聚合并计算窗口增量。
2. gRPC 连接断开时可能出现“服务端已处理，但客户端没收到 ACK”。Agent 重连时先拿到控制面已接受的最大序列，再决定下一批；服务端拒绝不递增序列，因此重发不会重复应用。
3. 调度不能直接跟着瞬时指标变化。普通波动先做 EWMA，再要求恶化连续 2 个样本、改善连续 3 个样本；原始 CPU/内存/磁盘命中硬门槛则立即摘除。恢复还要经过 30 秒冷却和 60 秒渐进增权。

### 结果

在确定性 12,000 请求模型中，自适应策略把错误率从 5.2083% 降到 0.2000%，P99 从 219 ms 降到 16 ms。Agent 在 10 秒空载窗口中的单核 CPU 约 0.1%，全 eBPF 模式峰值 RSS 约 23.63 MiB。这些数字分别是算法回归和虚拟化环境测量，不能伪装成线上数据。

## 3. 架构怎么讲

### 3.1 为什么 Go + C++

- C++ Agent：方便直接使用 libbpf 和内核 UAPI；RAII 可以管理 `bpf_object`、`bpf_link`、Ring Buffer 与 gRPC Stream；部署时不依赖 JVM 等运行时。
- Go 控制面：goroutine 与 gRPC 服务端适合处理大量长连接；标准库 HTTP 方便提供 API；`sync.RWMutex` 保护内存状态，测试和 race detector 能验证并发访问。
- Protobuf：把跨语言字段、类型、单位和兼容规则固定在协议里，避免手写 JSON 协议漂移。

好的回答不是“Go 并发高、C++ 性能高”就结束，而是说明语言边界与组件职责匹配。

### 3.2 一次指标上报经过什么路径

1. Agent 启动后读取 Boot ID，建立 gRPC 双向流并首先发送 `AgentHello`。
2. 控制面校验 `node_id`，按 `node_id + boot_id` 识别节点生命周期，返回此前接受的最大序列。
3. C++ 采集 procfs；启用 eBPF 时再读取 per-CPU Map、消费 Ring Buffer，并计算相邻窗口增量。
4. Agent 组装 `MetricBatch`，包含 sequence、采样时间、指标和最多 1,024 条内核事件。
5. 控制面限制每批最多 2,048 个指标与 1,024 个事件，过滤空名称、NaN 和 Inf。
6. Store 在写锁内检查 sequence、合并最新指标、计算状态机并刷新路由快照。
7. 控制面返回 ACK；Agent 只有看到 `accepted_sequence >= 当前 sequence` 才认为发送成功。
8. HTTP API、Prometheus Exporter 与网关读取深拷贝快照，不持有 Store 内部 map 引用。

### 3.3 为什么只存最新快照

控制面内存 Store 的职责是实时决策和查询，不承担历史时序存储。长期指标交给 Prometheus，这样避免在业务代码里重复实现压缩、保留策略、PromQL 和降采样。

代价是控制面重启会丢失节点历史、序列与状态机状态。生产化可以把节点元数据与状态检查点写入持久化存储，同时保持高频样本走 TSDB；多副本控制面还需要明确 leader 或一致性模型。

## 4. 功能开发与实现难点

### 4.1 procfs 指标

CPU 利用率不能直接读取一个现成百分比。Agent 两次读取 `/proc/stat`，计算总时间与 idle 时间的差值：

```text
cpu_usage = 100 * (delta_total - delta_idle) / delta_total
```

差值法能抵消系统启动以来的累计量。网络速率同理，对 `/proc/net/dev` 的累计字节做相邻采样差，再除以时间间隔。内存利用率使用 `MemTotal` 与 `MemAvailable`，后者比只看 `MemFree` 更符合 Linux 页缓存可回收语义。

常见追问：为什么不用内核模块？这些稳定的低频累计指标已经由 procfs 暴露，内核模块会增加崩溃面、版本适配和权限成本，没有必要。

### 4.2 调度等待延迟

`sched_wakeup`/`sched_wakeup_new` 记录任务进入 runnable 状态的单调时钟时间，以 PID 为 key 写入 Map；`sched_switch` 在任务真正运行时取出开始时间并计算差值。

这个延迟回答的是“任务已经可运行，但等了多久才拿到 CPU”，比 CPU 利用率更接近调度竞争。PID 关联存在复用和未完成项问题，因此 Map 必须有容量边界，并在消费后删除对应 key。

### 4.3 块 I/O 延迟

探针在 `block_rq_issue` 记录请求下发时间与读写方向，在 `block_rq_complete` 使用同一个 `struct request *` 查找并计算延迟。in-flight Map 使用有上限的 LRU，防止完成事件缺失时无限增长。

为什么不能只看吞吐或 IOPS？吞吐量高不等于请求体验好，少量慢请求会抬高 P99；读写路径的延迟特征也不同，所以分别聚合。

### 4.4 TCP RTT、重传和 RST

`tcp_probe` tracepoint 提供平滑 RTT，探针按 2 的幂次分桶；`tcp_retransmit_skb`、`tcp_receive_reset`、`tcp_send_reset` 同时增加计数并尝试写 Ring Buffer 事件。

RTT 上升只能说明往返确认变慢，重传还可能由丢包、乱序、拥塞或超时触发。RST 表示异常关闭线索，但不能仅凭一个 RST 就判定服务故障，必须结合速率、方向、进程和时间窗口。

### 4.5 为什么用对数直方图

如果每个事件都上报，调度和网络热路径会产生大量数据。32 个 `2^n` 桶能用固定内存覆盖很大的延迟范围，内核只做查表与自增，用户态从窗口增量估算 P95/P99。

代价是分位数返回桶上界，精度随桶宽变化。需要更精确时可以改用 HDR Histogram 风格的多级桶，但会增加 Map 大小和读取成本。

### 4.6 per-CPU Map

同一个全局计数器被所有 CPU 原子更新会造成 cache line 竞争。per-CPU Array 为每个 CPU 保存独立值，eBPF 热路径在当前 CPU 上普通自增，用户态读取后求和。

代价是内存使用量乘以可能 CPU 数，用户态读取成本也更高。本项目 Map 很小、采集频率低，这个交换合理。

### 4.7 Ring Buffer 可靠性

Ring Buffer 适合把可变速率事件从内核推到用户态，并保持跨 CPU 的事件顺序。可靠性设计有两道边界：

- 内核 `bpf_ringbuf_reserve` 失败时增加 per-CPU dropped 计数；
- 用户态单批最多保留 1,024 条，超过后增加 userspace dropped。

Agent 把两类丢失合并为 `kernel.ring_buffer.dropped`。面试时要主动说明 Ring Buffer 不是“绝不丢失”的队列；有界、可观测、不会反压内核热路径才是目标。

### 4.8 CO-RE 与 BTF

CO-RE 即 Compile Once – Run Everywhere。Clang 在 BPF ELF 中保留字段重定位信息，libbpf 加载时读取目标内核 BTF，修正结构字段偏移。

项目只声明探针真正读取的最小结构字段，不提交某台机器生成的完整 `vmlinux.h`。CO-RE 能缓解内核结构布局差异，但不能保证所有内核都有需要的 tracepoint/BTF，也不能消除语义变化，因此加载失败必须显式报告。

### 4.9 gRPC 断线与幂等

网络的关键歧义是：服务端处理完成后连接断开，客户端没有收到 ACK。若直接生成新序列，可能丢失确认；若盲目重发，又可能重复计算。

本项目使用单调 sequence：Store 只接受 `sequence > last_sequence`。同 Boot ID 重连时 Hello ACK 返回已接受序列；若重发已经处理过的批次，控制面不再次应用，但 ACK 仍告诉 Agent该序列已接受。这是以节点启动周期为范围的幂等处理。

它不是严格 exactly-once：控制面状态未持久化，重启后无法保持去重历史。更准确的术语是“至少一次传输下的幂等应用语义（单控制面进程生命周期内）”。

### 4.10 EWMA、硬门槛、滞回与冷却

EWMA 公式：

```text
S(t) = alpha * X(t) + (1 - alpha) * S(t-1), alpha = 0.35
```

普通评分使用平滑值，减少瞬时尖峰引起的状态抖动。硬门槛必须读取原始值，否则 100% CPU 可能被历史低值稀释而延迟摘除。

- 普通恶化：连续 2 个同方向样本后迁移；
- 普通改善：连续 3 个样本后迁移；
- 硬门槛：立即 unhealthy；
- unhealthy 恢复：先等 30 秒，再累计 3 个改善样本；
- 恢复可路由后：权重从 10% 起，在 60 秒内线性升到 100%。

这体现“快速失败、谨慎恢复”。滞回解决状态来回跳，冷却解决故障刚消失就立刻回流，渐进增权解决恢复节点被瞬间打满。

### 4.11 权重归一化与平滑加权轮询

路由策略先计算原始权重：healthy 使用健康分，degraded 再乘 0.5，断连/unknown/unhealthy 为 0，恢复节点再乘 ramp factor。

浮点权重转整数时使用最大余数法：先向下取整，再按小数余数从大到小补齐，保证所有可用节点权重严格等于 10,000。这比逐项四舍五入更容易保持总和不漂移。

假网关使用平滑加权轮询。每轮给每个节点的 current weight 加上 effective weight，选择最大者，再减去总权重。它比随机抽样更确定，短窗口分配也更平滑，便于测试。

### 4.12 路由版本与 ETag

只有路由内容变化时版本才递增。网关携带 `If-None-Match` 轮询，未变化时控制面返回 304，减少 JSON 传输和解析。网关必须缓存最近一次成功快照，并拒绝更小版本号的响应覆盖当前配置。

这还不是强一致配置分发：网关轮询存在传播延迟。需要更快收敛时可以增加服务端流式推送，但仍保留版本号用于乱序保护和断线恢复。

## 5. 高频八股与参考回答

### eBPF 程序为什么安全

加载前 verifier 会检查有界控制流、指针访问、栈使用和 helper 调用是否合法；通过后才允许执行。安全不等于没有业务风险：错误的挂载点、过大的 Map、过高事件率仍可能造成开销，因此还要做权限收敛、容量限制和压测。

### tracepoint、kprobe、fentry 怎么选

- tracepoint：稳定的显式 ABI，字段相对稳定，本项目优先使用；
- kprobe：可挂内核函数但更依赖符号与实现细节；
- fentry/fexit：基于 BTF，开销低且类型信息好，但对内核能力要求更高。

### Ring Buffer 和 Perf Buffer 区别

Ring Buffer 是共享的 MPSC 缓冲区，可维持跨 CPU 事件顺序并减少每 CPU 独立缓冲的内存浪费；Perf Buffer 通常按 CPU 分配，消费模型成熟但跨 CPU 顺序和内存使用不同。二者都可能在消费者跟不上时丢数据。

### gRPC 双向流底层是什么

gRPC 通常运行在 HTTP/2 上，一个长期 stream 内双方都能持续发送消息，具备多路复用、流量控制和头部压缩。Protobuf 解决序列化和 schema 兼容，不自动解决业务幂等、重试风暴或消息持久化。

### Protobuf 如何做兼容升级

新增字段使用新编号；删除字段后应 reserve 原编号和名称；不要改变既有字段含义或复用编号；枚举要考虑 unknown 值。字段缺失使用默认值，所以业务层仍需校验必填语义。

### 为什么需要 Boot ID

sequence 只在一次 Agent/系统启动周期内有意义。节点重启后从 1 开始，如果只按 node ID 去重会把新批次误判为已经处理。Boot ID 变化时清空序列、EWMA、候选状态和冷却；相同 Boot ID 的网络重连则保留这些状态。

### mutex 会不会成为瓶颈

当前 Store 用一个 `RWMutex` 保证节点更新、评分和路由快照的一致性，读操作拿读锁并深拷贝。它实现简单、适合当前规模。节点数和上报频率提高后，可按 node ID 分片、把路由计算移出全局写锁、用不可变快照 + atomic pointer 发布，并通过 benchmark 决定是否优化，而不是先入为主地拆锁。

### P95/P99 是怎么计算的

读取当前累计直方图，减去上一个窗口快照得到增量；计算总样本数与分位目标，按桶累加到达目标的第一个桶，返回该桶上界。优点是固定内存和低热路径成本，缺点是近似值。

### 为什么健康分不能直接作为结论

健康分是策略输入，不是根因诊断。相同分数可能由不同资源组合造成；节点是否适合新流量还取决于硬故障、连接状态和恢复阶段。因此 API 同时保留原始指标、分数、状态和 reason。

### Prometheus 的 Counter 和 Gauge 怎么选

单调累计量用 Counter，例如节点累计内核事件；当前值、状态和窗口值用 Gauge，例如 CPU、健康分、P99 和窗口 dropped。进程重启导致 Counter 归零由 PromQL 的 `rate/increase` 处理。

### 为什么不把所有指标写 MySQL

高频时序数据写关系库会带来大量写放大、索引和保留策略负担。Prometheus 更适合时间序列抓取、压缩和查询；关系库适合节点元数据、用户配置、告警规则和审计记录。

## 6. 面试官可能追问的缺陷

回答缺陷时用“当前边界 + 为什么 + 怎么演进”三段式。

### 控制面单点

当前内存 Store 是单进程，优点是状态机与路由一致、便于验证。生产化可以增加 leader 选举或基于一致性存储的单写者模型，路由快照通过版本发布；不要让多个副本独立计算并同时下发冲突版本。

### 没有 TLS 和鉴权

开发环境使用 insecure gRPC。生产必须使用 mTLS 验证 Agent 身份，证书绑定 node ID；HTTP 管理面增加认证、RBAC、审计和网络隔离。

### Agent 需要特权

开发容器为了验证使用 privileged。生产不应这样部署，应根据内核版本收敛到 `CAP_BPF`、`CAP_PERFMON` 等能力，配合只读文件系统、seccomp、签名包和探针白名单。

### 指标和事件可能丢失

事件通道有界是主动设计。正常窗口观察 dropped 指标并告警；过载时优先保系统稳定。可进一步做事件采样、按类型限流、增大缓冲、提高消费频率或只保留聚合结果。

### 路由实验不是真实线上流量

确定性实验用于可复现地验证算法，不宣称线上收益。真正上线前要做影子决策、灰度、按业务分层的回放、真实 SLO 对比，并准备一键回退到稳定策略。

## 7. 测试与质量怎么讲

项目不是只跑一次演示：

- Go 单测覆盖评分、滞回、冷却、Boot 重置、Store 序列、HTTP ETag、Prometheus 和路由分配；
- `go test -race` 检查并发数据竞争，`go vet` 做静态检查；
- CTest 用夹具和构造直方图验证 procfs 解析、窗口增量与 P95/P99；
- 跨语言 E2E 启动真实 Go 控制面和 C++ Agent，验证重连后 sequence 从 2 继续；
- 路由 E2E 启动健康与过载 Agent，验证过载节点权重 0，10,000 个请求全部进入健康节点；
- Linux 特权回归真正加载 BPF 对象，并使用 stress-ng、fio、netem/iperf3 制造信号；
- 确定性 benchmark 固化为 golden Markdown，CI 比对输出，防止算法结果静默变化。

公共 CI 不运行特权 eBPF，因为 GitHub Runner 内核权限不可控；把环境限制误判成代码失败没有意义，所以特权测试使用显式本地脚本。

## 8. 简历表述建议

可以写成以下 4 条，数字都能在仓库报告中找到：

1. 使用 C++20、libbpf CO-RE 开发 Linux 节点 Agent，基于 procfs 与 eBPF 采集 CPU/内存/网络、调度等待、块 I/O P99、TCP RTT/重传/RST，并通过 per-CPU 直方图和有界 Ring Buffer 控制热路径开销。
2. 使用 Go 与 gRPC 双向流实现控制面，设计 Hello/sequence/ACK/Boot ID 协议，支持重复批次幂等处理、断线续传语义和 1–30 秒指数退避。
3. 实现 EWMA + 硬门槛 + 滞回 + 冷却的节点状态机，以及异常摘除、恢复渐进增权和总权重 10,000 的平滑加权轮询；固定 12,000 请求模型中错误率由 5.2083% 降至 0.2000%。
4. 建立 Go race/vet、C++ CTest、跨语言/路由 E2E 与 stress-ng/fio/netem 故障注入体系；10 秒空载测量中 Agent 单核 CPU 约 0.1%，全 eBPF 模式峰值 RSS 约 23.63 MiB。

不要写“性能提升 96%”而不说明是确定性模型，也不要写“零丢包”。正常 TCP 测试丢失率为 0%，过载测试刻意得到 96.43% 丢失，二者口径不同。

## 9. 代码导读路线

## 10. 最后的回答原则
